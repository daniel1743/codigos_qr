# Cripqer — Block Cardinality, Duplicates and Add-Content UX Audit V1

**Status:** `CRIPQER_BLOCK_CARDINALITY_DUPLICATE_AUDIT_COMPLETE`

**Mode:** Read-only forensic audit. No Sidebar, reducer, schema, renderer, template, or cardinality rule was changed for this audit.

## Executive findings

1. `profile.banner` and `profile.avatarUrl` are structural profile media, not blocks. Their authority is singleton by schema shape and they already render in header order.
2. Every item in the Blocks tab is currently addable repeatedly. `addBlock`, `insertBlock`, and `insertBlocks` append or insert without type/cardinality checks.
3. Section presets also append their generated blocks. Clicking a Hero preset does not replace the existing Hero; it inserts another Hero (and any companion blocks in that preset).
4. The renderer iterates `visibleBlocks` and resolves each item through `BlockRegistry`; it does not enforce uniqueness. Persistence serializes the same array, so duplicates survive save/reload.
5. The validator rejects duplicate block IDs, but not duplicate block types. Fresh IDs generated by `createBlock` and `b` therefore make repeated types valid at the current validation layer.
6. `TemplateRenderer` suppresses `ProfileHeader` when any authored `hero` block exists (`hasAuthoredHero`). Multiple Hero blocks still render in the blocks grid, making Hero duplication a P0 structural trap.

## Current authority and behavior

| Concern | Current authority | Current behavior |
|---|---|---|
| Add block | `src/premium-template-studio/components/editor/Sidebar.tsx` | `dispatch({ type: "addBlock", blockType })`; always appends a fresh block. |
| Add preset | `Sidebar.tsx` + `SECTION_PRESETS` | `dispatch({ type: "insertBlocks", blocks: preset.createBlocks() })`; always inserts the preset output. |
| Block mutation/history | `src/premium-template-studio/state/templateReducer.ts` | `commit` records the prior config in `past`; delete, undo and redo are generic and ID-based. |
| Render order | `src/premium-template-studio/engine/TemplateRenderer.tsx` | Blocks render in array order; profile header media is outside the block array. |
| Render support | `src/premium-template-studio/engine/BlockRegistry.ts` | All 40 registered block types resolve to a renderer; no uniqueness policy exists. |
| Persistence validity | `TemplateValidator.ts` + StudioProvider save path | IDs/types/URLs are checked; block-type cardinality is not checked. |
| Templates | `TemplateFactory.ts`, `TEMPLATE_DEFINITIONS` | Template switch uses `replaceConfig`; switching can replace the document, while Add Content does not replace existing sections. |

## P0 duplicate traps

### Hero

`hero` is one semantic region in the current product model. The six Hero presets use different variants and often add companion blocks, which is strong evidence they are alternatives rather than independent repeated Hero sections. Current behavior is unsafe:

- pressing any Hero preset appends a new `hero` block;
- a second Hero changes `hasAuthoredHero` behavior and suppresses the profile header;
- multiple Hero blocks then render in array order;
- no Add control becomes disabled.

Recommended future behavior: a Hero preset should offer “Aplicar estilo”/replace-or-merge semantics against the existing Hero, while preserving a deliberate advanced escape hatch only if product explicitly wants multiple narrative regions.

### Global action/navigation surfaces

`floatingActions` and `bottomNav` are global presentation structures. Duplicate instances can overlap or compete. `booking`, `calendar`, and `qr` can also create competing primary conversion/scheduling surfaces. These need product decisions before generic Add remains unrestricted.

## P1 UX inconsistencies

- Generic blocks have no count, state, or explanation even when the block owns a semantic collection and a second copy is usually unnecessary.
- Preset buttons do not disclose that they append blocks rather than replace an existing section.
- The structure list exposes move/delete per ID but provides no type-level duplicate warning.
- `TemplateValidator` catches duplicate IDs only; it does not report duplicate semantic types.
- Add and template-switch semantics differ: Add appends; template switching replaces config and resets history. This distinction is not surfaced in the UI.
- Trust signals are the one explicit limited collection (`MAX_TRUST_SIGNALS = 4`), but the same bounded-cardinality language is not generalized to parent blocks.

## Repeatable blocks that should remain unrestricted

`heading`, `text`, `links`, `featuredLink`, `buttonGroup`, `cta`, `video`, `image`, `gallery`, `mediaCard`, `document`, `divider`, `spacer`, `featuredMedia`, `product`, `music`, and `carousel` have coherent reasons to recur. Their collections are scoped to each instance, and renderer behavior is naturally array-based.

`social`, `portfolio`, `contact`, `map`, and `tabs` should remain technically repeatable but receive contextual guidance or a future “distinct context” label rather than a hard global singleton rule.

## Uncertain cases requiring product decision

1. Whether a page may have multiple QR blocks for different destinations, or exactly one primary QR.
2. Whether `trust`, `stats`, `services`, `testimonials`, `pricing`, `faq`, and `timeline` are globally singleton or may repeat by domain/context.
3. Whether multiple portfolios/galleries are a supported multi-category workflow or merely an accidental duplicate path.
4. Whether a Hero preset should replace the Hero, preserve user-authored content while changing variant, or allow explicit multiple narrative regions.
5. Whether multiple maps/calendars/bookings are needed for multi-location businesses.
6. Whether `featuredMedia` is a repeatable project highlight or the one primary media story for a page.

## Smallest implementation plan after product decisions

1. Add a declarative cardinality policy outside the reducer, covering only confirmed singleton/limited types.
2. Make Sidebar Add controls state-derived and visibly disabled at the policy maximum; never hide them.
3. Route Hero presets through an explicit existing-Hero update/replace flow instead of `insertBlocks`.
4. Add non-block primary-media controls only through `profile.banner`/`profile.avatarUrl`, as already established.
5. Add reducer-level tests for add, delete, undo, redo, preset insertion, and template switching for each confirmed singleton.
6. Add validator warnings for duplicate semantic types only after the product policy is frozen; do not silently migrate existing documents.
7. Add runtime QA for mobile, save/reload, public rendering, and legacy documents containing duplicates.

## Test and evidence status

- Existing reducer tests cover generic add/delete/undo/redo mechanics, not semantic cardinality.
- Existing preset tests verify unique preset IDs, fresh block IDs, and valid preset construction; they do not assert replacement semantics.
- Existing renderer tests cover block/profile rendering contracts but do not reject duplicate semantic types.
- No code behavior was changed by this audit.
